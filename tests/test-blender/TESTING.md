# Actual Blender engine tests

This private workspace exercises the public source SDK and one-shot runtime against an explicitly supplied Blender installation. It creates a small CPU Cycles scene, renders a native PNG, saves a native `.blend` copy, reopens that copy in a fresh owned session, and independently inspects native geometry, shading, camera, lighting, and decoded image data. It also verifies that an ordinary script failure remains distinct from successful native shutdown and does not erase previously published files. MCP and upstream typia behavior are outside this suite.

Set `BLENDIA_BLENDER_EXECUTABLE` to the Blender executable and `BLENDIA_EXTENSION_SOURCE_DIRECTORY` to the actual extension packaging source directory. Prepare its ignored distribution license with the existing root command `pnpm extension:license` before running this source package. The target engine is Blender 5.2; unavailable or incompatible prerequisites fail explicitly rather than skipping or claiming a pass. After the workspace is wired and dependencies are installed, run `pnpm --filter @blendia/test-blender start`. TypeScript source packages execute without a build. Run the package's `build`, `lint`, and `evidence` scripts separately for their respective tool checks.

The suite first uses Blender's public `--command extension build`, registers an isolated offline USER repository, and runs `install-file --repo ... --enable`. A fresh native process loads that actual `bl_ext` addon, checks enabled registration and disable/enable behavior, compares every installed ZIP payload member with the built archive, and matches its license to the maintained repository-root LICENSE. Only the verified installed `__file__` directory supplies `headless_bootstrap.py` to all six scenarios. Installation failure stops the suite; it never switches to a source import. This native packaging and installation step is separate from a TypeScript distribution build and does not test manifest strings or typia behavior.

Optionally set `BLENDIA_TEST_OUTPUT_DIRECTORY` to an existing parent directory for retained runs. The runner reserves a unique child directory; otherwise it reserves one under the operating system's temporary directory. It prints that directory before execution and preserves the built extension ZIP, installed-payload observation, native PNG/.blend outputs, CPU seeds, native observations, and public runtime result reports on success or failure. Temporary bootstrap, descriptor, extension-repository, and Blender configuration storage uses a separate process-local child directory. No credentials or private bootstrap file bodies are copied into the reports. Upload only the explicit user files and reports, never the whole output tree: an unknown invocation can retain live private credentials beneath `private-runtime`. Cleanup never recursively removes a reported unknown invocation or published output.

The scene roundtrip uses a 128 by 128 CPU render with eight samples. It verifies PNG signature, dimensions, byte-stream continuity, equality of streamed and exported bytes, and native decoded pixel variation. It does not compare images to a snapshot or promise identical PNG hashes across Blender versions, machines, or repeated renders. A separate native load independently checks authored mesh vertices and face winding, material node inputs, camera aim, light parameters, and saved engine configuration. This is headless engine coverage, not automated clicks in Blender's graphical interface.

Five independent scenarios cover writer-lease rejection and reacquisition, object identity across real reconnect and fresh owned sessions, actual shared-mesh assignment refusal with independent native state inspection, no-camera and duplicate-render admission, four-artifact capacity and explicit release, and PNG/native-copy publication conflicts with explicit overwrite and preserved user backups. Each scenario reserves its own output directory and executes sequentially so a failure does not hide another behavior group. The small resource-admission renders use 32 by 32 pixels and the same CPU seed. Prepared source and checklist answers do not establish a passing run.

The publication scenario's existing native readback also decodes its complete 32 by 32 PNG and imports the actual ArtifactStore and BridgeError modules from the verified installed extension directory, without a source fallback. Real reserved files exercise complete adoption, metadata provenance, bounded reads, export and release, followed by rejection of the native PNG's 33-byte header, a prefix ending inside its first IDAT payload, a copy missing IEND and a changed IDAT data byte with its original checksum. A small chunk walk only locates the altered boundaries; it does not validate PNGs or reproduce the production checker. Every malformed-file result is collected before assertion, owned stages are discarded, the store closes, and original public outputs remain unchanged. The retained publication-native-observation.json records these results. This remains one of the six scenario groups and adds no native process; it does not induce disk-full failures or native callbacks, establish exhaustive codec compliance, or claim GUI acceptance.

The suite deliberately leaves GUI clicks, native render cancellation, real ten-minute TTL expiry, aggregate 128-MiB image capacity, ambiguous native callback ownership, filesystem publication racers, external-image autosave refusal, current-session rename/delete/undo/load, direct working-filepath before/after inspection, parent loss, and unknown/timeout retention unclaimed. The public SDK does not expose several of those native controls; the tests add neither product hooks nor private protocol fallbacks to manufacture coverage. Remaining actual-host observations must stay explicit in the testing tracker.

Native packaging, installation, seed generation, and independent readback each have a ten-minute observation budget. Their sanitized `native-observations/*.jsonl` journals record the stage, observed PID, UTC observation time, outcome, code, and signal. This budget does not apply to the user's TypeScript execution or its native toolchain preparation. An expired observation stops new native/recipe admissions, preserves private files and user outputs, and unrefs only the runner's direct child handle; it does not kill Blender, certify descendant termination, retry, or replay a mutation. A public headless `unknown` result closes the same admission barrier. Later groups are reported as blocked, while ordinary assertion failures with known lifetimes still allow other independent groups to run. Unknown outcomes are not intentionally induced by this suite.

## Manual native GUI acceptance

The following procedure reproduces the four acceptance areas in [GUI lifecycle #24](https://github.com/samchon/blendia/issues/24) from a source checkout. It is separate from the six automated headless groups and records no result until the native actions have actually been observed. Use a new PowerShell process dedicated to acceptance, an actual Blender 5.2 executable, a new owned acceptance directory and an expendable scene. Keep that process open through installation, GUI launch and project execution so its isolated settings remain consistent; its environment changes must not be applied to user or machine settings.

Replace the three paths, install the checkout's committed dependencies and prepare its canonical extension license. These commands build and install the actual ZIP in an isolated offline USER repository, then run the existing installed-payload and registration verifier. Check every command's exit status before proceeding; a failed step is not permission to import the source directory instead. The verifier compares all members of the new ZIP with the actual imported installation and records the observed payload count rather than assuming a historical count.

```powershell
$checkout = (Resolve-Path -LiteralPath 'D:/path/to/blendia').Path
$blender = (Resolve-Path -LiteralPath 'D:/path/to/blender.exe').Path
$acceptance = 'D:/acceptance/Blendia GUI 한글'
New-Item -ItemType Directory -Path $acceptance -ErrorAction Stop | Out-Null
Set-Location -LiteralPath $checkout
pnpm install --frozen-lockfile
pnpm run extension:license
$env:BLENDER_USER_CONFIG = Join-Path $acceptance 'config'
$env:BLENDER_USER_EXTENSIONS = Join-Path $acceptance 'extensions'
$repository = Join-Path $acceptance 'repository'
New-Item -ItemType Directory -Path $env:BLENDER_USER_CONFIG,$env:BLENDER_USER_EXTENSIONS,$repository | Out-Null
$archive = Join-Path $acceptance 'blendia-extension.zip'
& $blender --background --factory-startup --command extension build --source-dir "$checkout/blender/extension" --output-filepath "$archive"
& $blender --background --factory-startup --command extension repo-add blendia_acceptance --directory "$repository" --source USER
& $blender --background --command extension install-file "$archive" --repo blendia_acceptance --enable
& $blender --background --disable-autoexec --python-exit-code 1 --python "$checkout/tests/test-blender/assets/verify_installed.py" -- "$archive" blendia_acceptance "$repository" "$checkout/LICENSE" "$acceptance/installed-extension.json"
& $blender --disable-autoexec
```

In the new GUI, use Object Mode and enable Global Undo. Open the Blendia sidebar and select Start Blendia. Follow [Copy Session File Path](../../blender/extension/README.md#install-and-start) to load credentials privately into this dedicated PowerShell process; never print descriptor bodies, tokens or credential-bearing environment values. Prepare a new external project with a space and Unicode in its path using [the source-checkout setup](../../docs/design/script-jobs.md#set-up-an-external-source-checkout-project), and save the [SDK scene example](../../packages/sdk/README.md) as `src/scene.ts`. Its documented `pnpm blendia doctor` and `pnpm blendia run` commands use explicit project configuration and owned PNG/.blend destinations. Close each SDK client before another connects; keep the doctor's `execution: "not-tested"` distinct from the subsequent actual scene and render result.

1. **A1 — normal rendering and native Esc.** Record the working `bpy.data.filepath`, scene render filepath and caller UUID before starting. Run the scene example once to observe normal native completion and the same render identity, open its exported PNG in Blender's Image Editor, and compare working/render paths after publication. For a separate owned render with a new UUID and fresh output paths, choose a workload that permits observation of the real running job, record GUI progress and `bpy.app.is_job_running('RENDER')`, then press Esc in the actual render window. Observe the original job with `getRender` until its truthful terminal status, recording cancellation or uncertainty, artifact availability and owned-path restoration. A lost response is not a reason to issue the start again; do not assume a cancellation duration or call a native callback directly.
2. **A2 — undo, redo and file load.** Create an object through the SDK and retain its public handle, session and generation in credential-free JSON. Disconnect, perform actual Edit → Undo and Redo in the GUI, reconnect, and inspect the new generation and scene. Require old-handle invalidation (`STALE_HANDLE`, or `STALE_GENERATION` on an existing stale connection) and coherent newly obtained handles. Save an owned scene, use File → Open to load it, and repeat the generation/old-handle inspection. Reacquire Blender RNA references after loading; preserve partial scene effects and never replay the old mutation automatically.
3. **A3 — active Stop and disable retirement.** Use separate owned running renders for Stop Blendia and Preferences → extension disable. Record descriptor removal and failure of authenticated reuse, then test that starting a replacement session is refused while the old native owner is still retiring. Stop and disable revoke bridge access; neither proves native cancellation. Observe actual Esc or natural completion, callback retirement and render-path restoration before enabling/starting a new session. For captured launcher/private Text input lifetime, run the same project through the documented [TypeScript Macros controls](../../blender/extension/README.md#run-typescript-from-blender) and record terminal events, output EOF and outer CLI exit separately from private input cleanup or truthful unknown retention. Never infer descendant termination from a cleared process field.
4. **A4 — retain the observations.** Preserve the checked revision, engine version, ZIP/installed-payload report, owned scene and project inputs, public action/render IDs, observed PID identities, native progress/terminal observations, and separate EOF/cleanup results. Before Stop/disable, the Python Console can read `bpy.types.BLENDIA_OT_start.__module__`, the corresponding installed `server` module's `bridge.generation`, and public `bpy.app.handlers` lists for native callback ownership. Label console inspection separately from actual UI actions; do not modify result fields or invoke handlers. Record any unknown outcome and retain its owned files without retry or deletion. Quit normally, check the observed process identities, and close the dedicated PowerShell process only after recording its children and restoring or retiring its process-local settings. These steps do not establish GUI acceptance until the resulting evidence is reviewed.
