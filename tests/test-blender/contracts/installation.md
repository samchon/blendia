# Installed extension preparation

Apply these requirements to the suite preparation that builds, installs, and identifies the actual extension consumed by every real-engine scenario.

## Official installation

Use Blender's public extension packaging, offline repository, and install-file commands. Observe actual addon loading and registration; a ZIP filepath, copied source directory, manifest check, or import fallback cannot stand in for installation.

## Installed payload identity

Identify the actual imported installed module path and correlate its payload with the built ZIP. Supply that same installed core to subsequent headless scenarios and keep the maintained root license as the only license source.

## Isolated preparation lifetime

Keep preferences, extension repositories, temporary files, and outputs under invocation-owned paths with process-local configuration. Bound preparation/readback observation, record actual process ownership and status, stop new native admission after uncertainty, and distinguish that boundary from a user-script deadline or cancellation. Preserve failed or uncertain evidence, restore the runner environment, and avoid modifying the user's existing Blender setup or a second repository checkout.
