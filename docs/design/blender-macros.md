# Blender file and Text macros

Tracking: [#4](https://github.com/samchon/blendia/issues/4), with shared runtime work in [#3](https://github.com/samchon/blendia/issues/3) and actual verification in [#6](https://github.com/samchon/blendia/issues/6). [Draft #10](https://github.com/samchon/blendia/pull/10) adds the file and Text macro contract below to the live foundation merged in [#9](https://github.com/samchon/blendia/pull/9), preserving the source-first rules from [#11](https://github.com/samchon/blendia/pull/11). Source implementation and contract agreement do not establish successful Blender UI observations; verification results belong in the tracking issues and PR.

## Bounded scope

The viewport and Text Editor Blendia sidebars expose TypeScript Macros with Run TypeScript File, Run Active Text Snapshot, and Copy TypeScript Output. Settings identify the project directory, logical source path, optional project tsconfig, absolute Node executable, installed ttsc package metadata, CLI entry, and JSON string-array arguments. The saved-file action executes disk contents; it does not save a dirty Text buffer. Active Text execution snapshots the selected Text Editor datablock. Both reuse the authenticated live Blender session and existing shared runtime.

Consuming projects need the native TypeScript compiler and their imported SDK/npm packages and tsconfig plugins installed beforehand. Local execution uses source without a build: Python resolves the configured ttsc package's public `bin.ttsx`, then launches the configured Node executable with that launcher and `packages/cli/src/bin.ts`, without a shell. The outer launcher owns the CLI project; the CLI's project option selects the user's macro project. Local package exports remain TypeScript source, with separate distribution metadata. Do not require `lib` output, private ttsx imports, or compiled fallbacks.

Blendia's own existing tsconfigs explicitly opt out of automatic `@ttsc/lint` execution with its public `enabled: false` setting. Other configured and automatically discovered transformers, including the consuming project's typia integration, retain their normal policy; no blanket plugin bypass is added to the launcher. Development and CI run the additional `pnpm lint` guard against those same tsconfigs through the public `TtscCompiler`, while ordinary `ttsc` build, `ttsc --noEmit`, and the separate Wrtn Evidence checks remain in place. The guard discards compiler output captured in memory or temporary storage without producing package `lib`; it does not replace normal emit or transformer validation. This changes the configuration boundary, not the runtime or scene API, and establishes no measured speedup. See the [development command contract](../conventions.md#compiler-exports-and-commands).

The Python launcher requires a running bridge with no current client owner and permits one owned execution at a time. It snapshots settings and Text before launch, closes stdin, merges stdout/stderr, and drains output through a nonblocking timer. Each tick reads at most 64 KiB within a 4 ms budget; the retained UTF-8 tail is limited to 64 KiB and marks truncation. Reading continues after retention fills. Incremental decoding and token redaction preserve useful diagnostics while credentials remain environment handoff data, outside arguments and reported metadata. Direct Blender responsiveness still requires observation.

## Text handoff and staging

The CLI grammar is `blendia run-text --cwd <directory> --source-path <logical-path> --input-file <private-file> [--project <tsconfig>] [--origin <label>] [-- <script-arguments...>]`. The first three options are required; launcher options precede `--`, after which arguments are forwarded verbatim. Unknown, duplicate, empty, or missing launcher operands are refused. The private input is read as a regular file with strict UTF-8 decoding and a 262144-byte limit, then closed before launch. The CLI does not delete that externally owned input. The existing `run` command retains saved-file execution.

The shared [runTextMacro](../../packages/runtime/src/runTextMacro.ts) accepts [ITextMacroOptions](../../packages/runtime/src/ITextMacroOptions.ts): text plus the explicit cwd and sourcePath context, optional origin, and inherited project, args, and connection options. The snapshot is limited to 256 KiB of UTF-8. Source Path must name a non-declaration `.ts`, `.tsx`, `.mts`, or `.cts` file inside the project both lexically and through its real parent directory. The parent must exist and permit writing. Use a module with imports or exports; staging does not isolate global-script declarations.

Runtime creates an exclusive random, nonhidden sibling with the same TypeScript suffix and unchanged snapshot text, then delegates its entry to `runProjectScript`. [ITextMacroResult](../../packages/runtime/src/ITextMacroResult.ts) extends the direct launcher's code and signal with resolved sourcePath, actual stagedPath, origin, staging disposition, and optional cleanupError. Omitted origin uses the resolved logical source path. Ordinary direct-launcher exit permits removal only when the staged path still has its original filesystem identity. Signal termination, launch uncertainty, replacement, or cleanup failure retains the path and reports the reason; an abrupt parent crash can also leave it behind.

Python owns a separate private UTF-8 input file, closed before launch, and its directory. It removes that input after normal observed completion but retains and reports it when observation or termination is uncertain. Runtime owns only its sibling source; it does not remove Python's input. The original source, Text datablock, and tsconfig are never overwritten. A retained path is for recovery after resolving surviving execution, not an instruction to delete a file still in use.

This is module-macro staging with explicit origin metadata. The temporary path is the real compiler/runtime path, while the result can identify its originating Blender Text and intended source path. A stale on-disk source can still fail project checking, and the staged basename, module identity and `import.meta.url` differ. Do not present sibling staging as a full unsaved editor overlay, self-import replacement, IDE or LSP.

## Process limits and partial effects

There is no macro Stop action. Stopping the bridge revokes bridge access but does not cancel TypeScript or reverse previous Blender changes. Direct-launcher exit does not establish descendant shutdown. If inherited output remains open for two seconds after that exit, observation ends with an unknown-descendant status and retained input. Signal termination or observer failure also preserves uncertainty. Further launches remain blocked; resolve surviving descendants before restarting Blender and cleaning retained files.

Disabling the extension removes its controls while bounded draining and reaping continue without reading removed UI properties. Closing Blender can leave TypeScript processes and private inputs behind. No process-tree cancellation, transactional rollback, or retry is promised. A failed or interrupted macro can leave some scene edits applied; the output and staging disposition describe observed execution rather than a scene transaction. Controlled job cancellation remains later work.

## Acceptance

- A user can run an actual project file from Blender and observe its existing SDK operation and logs without leaving the UI.
- A user can run an edited active Text snapshot in explicit project context, with honest source/staging diagnostics, preserved original files and owned cleanup.
- Actual first-party logic receives meaningful units; direct Blender observations cover the supported UI/file/Text behavior. Do not add configuration, upstream, empty-import, package-distribution or artificial smoke suites.
- Complete the full applicable verification/review round, then require all configured CI on the exact source head before Ready and immediate merge.

## Following slices and sources

Material/camera operations, asynchronous render/jobs, artifacts, thin typia MCP with native images and later headless reuse remain following bounded slices. This UI slice preserves those goals without mixing their implementation into its acceptance. Existing Blender continues to own its engine, editor and renderer; Three.js, full bpy parity and universal synchronous addon callbacks remain outside scope.

Source-verified research and limitations are preserved in [#4's Stage 2 proposal](https://github.com/samchon/blendia/issues/4#issuecomment-6598702203). Relevant primary references are Blender's [Text API](https://docs.blender.org/api/5.2/bpy.types.Text.html), [ttsx execution](https://ttsc.dev/docs/ttsc/execute/), Python [nonblocking descriptors](https://docs.python.org/3.13/library/os.html#os.set_blocking), [subprocess ownership](https://docs.python.org/3.13/library/subprocess.html), Windows limitations of [select](https://docs.python.org/3.13/library/select.html), and Windows [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). These support the design; they are not executed UI/Text validation results.
