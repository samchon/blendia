# Owned one-shot headless proposal

Prepared on 2026-11-04 for the mission coordinator and the next Draft after GUI scene/render/save PR14. This is read-only design research, not an implemented capability or an execution-success claim. No repository source, Git state, installation, Blender process, product probe, or benchmark was changed or run while preparing it.

## Scope and API

Use one `runHeadlessProject(options: IHeadlessProjectOptions): Promise<IHeadlessProjectResult>` entry, with each named interface in its own file. Options reuse the current project entry/cwd/project/args context, add an explicit Blender executable and optional input .blend, and define bounded startup/shutdown observation deadlines. The owned private bridge supplies the script connection; a caller's existing GUI connection must not be adopted or overridden. Deadline defaults and CLI spelling are next-Draft details, not measured startup promises.

Require `extensionDirectory: string` to name the actual extracted Blendia extension root, explicitly supplied by the caller. In a source checkout this can be `blender/extension`; after ZIP installation it is the user's actual installed extension directory, with no repository-relative runtime default or automatic search. The next headless Draft packages `headless_bootstrap.py` beside the shared Python core in that same extension ZIP; the runtime passes its resolved absolute path to Blender's public `--python` option. The bootstrap locates/imports its colocated core from its own file location without registering the GUI, rather than copying Python sources into the TypeScript runtime distribution. A missing bootstrap or incompatible extension is a prerequisite failure, not a reason to fall back to an unrelated checkout. The current PR14 ZIP is not claimed to contain this future entry point, and this preparation adds no PR14 gate.

The result keeps the script's existing terminal snapshot distinct from the owned Blender's raw code/signal and the composite lifecycle observation. Preserve bounded script and Blender logs with separate provenance and explicit retention loss; never merge one process's status into the other's. Report retained task paths and sanitized diagnostics when observation is uncertain. A composite normal closure does not convert a nonzero script result into success or certify the scene. This API is a foreground one-shot, not a persistent MCP editing session or a daemon.

## One lifetime owner

The runtime reserves task-owned private storage, resolves explicit paths, and starts exactly one new Blender child through the existing internal process owner with shell:false, windowsHide:true and bounded capture. Reuse ScriptProcess and ScriptLog policy rather than creating a second spawn/lifecycle engine. Extend internal process observation only where the real Blender owner needs a startup/close observer; do not add a public process manager.

Pass ordered public CLI arguments: `--background --factory-startup --disable-autoexec`, optional input .blend, `--python-exit-code 1 --python <absolute bootstrap.py> -- <absolute private configuration>`. Credentials are absent from argv and public stdout. The factory flag skips the user's startup.blend; it is not a claim that every preference, driver, or external render dependency is isolated. The optional .blend must load before the bootstrap and before any settings whose values loading can replace. [Blender 5.2 CLI arguments](https://docs.blender.org/manual/en/5.2/advanced/command_line/arguments.html).

The bootstrap creates an authenticated loopback bridge in this invocation's private directory, publishes bounded versioned readiness metadata only after binding, and remains in a synchronous main-thread request pump. Runtime authenticates private readiness without taking the script's exclusive SDK lease, then uses the existing captured ScriptJob/public ttsx path for the original project TypeScript. The TypeScript script connects to this same owned bridge, calls the shared scene/render/save methods, and disconnects normally. Local execution stays source-first without a build, extra embedded runtime, or additional package dependencies.

After a known script terminal result, the lifetime owner requests orderly bootstrap completion and observes both Blender closure and pipe EOF. A minimal private control connection, authenticated separately from the exclusive SDK owner, can carry completion and detect parent EOF between commands; it must not consume the scene writer lease or expose a new public daemon/session API. Keep this internal and bounded. Parent loss, lost control, or incomplete shutdown never authorizes replay. Startup timeout means readiness was not observed, not that Blender cannot still be starting.

## Main thread and finite conditions

Official creator.cc dispatches final command-line arguments and then takes the background exit path; GUI mode takes WM_main. Therefore registering a timer and returning from a background --python script is not a persistent request server. Keep the bootstrap script executing until its explicit stop condition, close owned transport, and return; ordinary background teardown then follows. This does not impose a finite wall-clock bound on a blocking native call. [Versioned Blender creator.cc](https://github.com/blender/blender/blob/blender-v5.2-release/source/creator/creator.cc), [official main source](https://github.com/blender/blender/blob/main/source/creator/creator.cc).

All bpy access, including scene validation, mutations, rendering, saving, handle resolution and transport dispatch into bpy, occurs on that one thread. Idle waits use standard-library socket/select or short sleeps; they do not move Blender work to a thread. The official threading warning rules out keeping a Python worker that touches Blender data alive beside rendering. [Blender threading guidance](https://docs.blender.org/api/main/info_gotchas_threading.html), [Blender 5.2 background flag](https://docs.blender.org/api/5.2/bpy.app.html#bpy.app.background).

## Reuse agreed with PR14 owners

The scene owner confirmed `scene_data.SceneData(commands)` as the reusable data layer: `validate(method, params, scene)`, `inspect(params, scene)`, and `apply(method, prepared, scene, mark_changed)`. The last method mutates bpy.data with no operator, area, global-undo or retained-RNA dependency. Background dispatch skips only the GUI undo/context adapter and preserves finite/topology/shared-mesh/linked-data validation, session/generation/UID identities, fresh resolution, and early effects marking. The current GUI adapter's native UNDO behavior stays intact.

The rendering owner confirmed `artifacts.ArtifactStore`, `file_publish.OwnedStage`, and `save_scene.save_blend_copy(bridge, params)` as shared persistence seams. GUI `native_render.NativeRender` uses a native WM job and explicitly rejects background mode. Add a background adapter using blocking native `EXEC_DEFAULT` with an explicit scene and `write_still=True`; do not pretend the GUI invoke/window/modal path works without a window. Reuse artifact publication, scene validation and save-copy behavior. [Render operator API](https://docs.blender.org/api/5.2/bpy.ops.render.html), [native render implementation](https://github.com/blender/blender/blob/blender-v5.2-release/source/blender/editors/render/render_internal.cc).

PNG and .blend persistence must be explicit operations in the same user TypeScript scene script. Reuse the PR14 native artifact staging/publication and overwrite policy; do not infer successful persistence from process exit or automatically save during shutdown. The headless process starts a fresh session: handles from GUI are not portable, while explicit saved files survive the process and are not temporary bootstrap cleanup targets. [Native save-copy API](https://docs.blender.org/api/5.2/bpy.ops.wm.html#bpy.ops.wm.save_as_mainfile), [native save implementation](https://github.com/blender/blender/blob/blender-v5.2-release/source/blender/windowmanager/intern/wm_files.cc#L4004).

Bridge artifact IDs and bridge-owned PNG files expire with their Blender session; they are not persistent GUI artifact URIs after an owned headless process exits. Only PNG/.blend files explicitly published to user-selected output paths persist independently under that output contract. A future MCP one-shot result may expose an actually runtime-owned bounded copy or an explicit user output, with its real owner and lifetime, and must not present an expired bridge artifact as a durable resource. This distinction adds no output API or daemon to the proposed slice.

## Unknown outcomes and Windows

A blocking render can prevent the main-thread pump from observing control or SDK timeouts until rendering returns. Timeouts, transport loss, signals, Windows high-bit unsigned statuses, missing EOF or a lost completion message remain unknown; do not retry a mutation, claim rollback, or remove uncertain owned staging. Retain private bootstrap/input/staging metadata when it may still be in use, report artifact existence separately from completion, and preserve existing bounded-log gaps. Successful native writes may remain after an unknown caller outcome.

On Windows, Node's ordinary kill signals are forceful, not an orderly Blender shutdown mechanism. The first slice requests cooperative completion only of its own child. Never enumerate/kill existing user Blender processes; never claim that killing the owned direct child terminates unknown renderer descendants. No taskkill tree sweep, OS JobObject guarantee, automatic cancellation, or process-group ownership promise is introduced. If an owned Blender fails to close, report unknown and the retained ownership information; termination escalation requires a separate explicit product decision. [Node child-process termination](https://nodejs.org/api/child_process.html#subprocesskillsignal).

## Proposed ownership and acceptance

Runtime/CLI owner owns the one-shot TS wrapper, named options/result, internal child observation reuse, private bootstrap paths, bounded logs and real command adapter. Python scene owner owns background bootstrap/main-thread routing and shared datacore integration. Rendering owner owns the blocking render adapter and shared publication/save boundary. SDK method contracts stay those of PR14; documentation and tests keep their existing owners. Delivery establishes the next issue scope and Draft before any implementation.

Use the same secret-free TypeScript scene consumer for GUI, headless and later MCP acceptance, explicitly producing a PNG and .blend. Observe owned PID creation, private ready identity, actual SDK operations, render/save results, script terminal status, cooperative Blender exit, EOF and retained/cleaned paths. Preserve actual TS/PNG/.blend outputs. Meaningful units may cover any real new option or lifecycle decision logic; no fixture child, compiler/import probe, benchmark or automated integration suite is introduced. Windows cooperative shutdown and the background pump remain actual-host acceptance criteria, not facts established by this memo.
